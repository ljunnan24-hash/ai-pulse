# 部署与数据说明

本文说明：**你需要在环境/数据库上完成的手动步骤**，以及 **MySQL 里会存哪些信息**（表与用途）。

---

## 一、你需要做的

### 1. 执行数据库迁移（必做，若尚未执行）

新功能依赖 **`issue_events` 表** 与 **`raw_items.event_id` 列**（多源聚合成「事件」）。

在 MySQL 中（已 `USE aipulse;` 后）执行：

```sql
SOURCE /path/to/ai-pulse/sql/migrations/2026-05-02_issue_events.sql;
```

或把该文件内容复制到客户端执行。  
**全新环境**也可以只用根目录的 `sql/schema.sql` 全量建库（已包含上述结构）。

后台信源管理依赖 `rss_sources` 表。若线上库没有自动建表权限，需额外执行：

```sql
SOURCE /path/to/ai-pulse/sql/migrations/2026-06-24_rss_sources.sql;
```

### 2. 配置环境变量

复制 `backend/.env.example` 为 `backend/.env`，至少配置：

| 变量 | 说明 |
|------|------|
| `DATABASE_URL` | MySQL 连接串（与 `sql/schema.sql` 中库名 `aipulse` 一致） |
| `PUBLIC_APP_URL` / `FRONTEND_URL` | 确认邮件、退订、管理页链接 |
| `LLM_API_*` / `DOUBAO_*` | LLM 周报生成（`generate_weekly` 需要；新部署优先用 `LLM_API_*`） |
| `SMTP_*` / `MAIL_FROM` | 发信（`send_weekly`、确认信） |
| 各类 `*_RSS_URLS` / `GITHUB_TOKEN` | 抓取源（见 `.env.example` 注释） |

> 历史项 `ENABLE_EVENT_MERGE` 已废弃；合并结果现由 **`issue_events` 表** 持久化，可不必配置。

### 3. 验证（建议）

迁移完成后可任选：

- **快速检查表结构**（需已配置 `.env` 中 `DATABASE_URL`）：  
  `cd backend && python -m scripts.check_db_schema`  
  应输出 `OK: issue_events table and raw_items.event_id present.`
- 启动 API：`cd backend && python -m uvicorn app.main:app --reload --host 0.0.0.0 --port 8000`
- 跑一期生成（需已配 RSS/LLM API 等）：`python -m app.jobs.generate_weekly`  
  成功时日志应出现 `Issue events rebuilt for issue ...: N clusters.`
- 在库里检查：表 `issue_events` 有行；`raw_items.event_id` 有非空值（有合并时）

### 4. 生产环境注意

- 服务器时区建议 **Asia/Shanghai**（与周刊周期 `current_period_monday` 一致）。
- Cron 示例见 `deploy/crontab.example`。

### 5. 来源优先级（PRD §五，已实现于评分）

RSS 在 `.env` 中按 `OFFICIAL_RSS_URLS` / `MEDIA_RSS_URLS` / `X_RSS_URLS` / `META_RSS_URLS` 区分 **P0–P4**，抓取时写入 `source_tier`，与 GitHub 条目（P2）一起参与 **百分制评分加权**（越接近官网权重越高）。无需额外配置项。

## 二、数据库里会存哪些信息？

以下为 **当前设计下** 各表存储内容概要（不含索引名细节）。

### `subscribers`（订阅者）

- 邮箱、订阅模式（simple/normal）、关键词 JSON、状态（pending/active/unsubscribed）
- 确认/退订/管理用的 token、创建与确认时间

### `weekly_issues`（周刊期次）

- 周期起始日 `period_start`、状态（draft/ready）、就绪时间
- 本期生成结果：`simple_text`、`normal_text`、`glossary_json`、**完整结构化 `payload_json`**（邮件渲染用）
- **当前最新一版**始终写在本表；同一 `period_start` 多次 `--force` 重跑会覆盖上述字段

### `weekly_issue_snapshots`（周刊生成历史，可选但强烈推荐）

- 每次 **`generate_weekly` / `build_weekly_multi_agent` 成功标记 ready** 时 **追加一行**，不删除旧行
- 字段含当期 **`payload_json` 全文**、**`audit_report_json`**（多 Agent / 送达率审计等）、**`source`**（如 `generate_weekly`、`generate_weekly_force`、`build_weekly_multi_agent`）、**`created_at`**
- 按 **`issue_id` 或 `period_start` + `created_at`** 即可对比「哪一版出了什么问题」
- 迁移：`sql/migrations/2026-05-05_weekly_issue_snapshots.sql`（全新库也可用根目录 `sql/schema.sql`，已含该表）

### `raw_items`（抓取原始条目）

- 归属哪一期 `issue_id`、可选归属哪个聚合事件 **`event_id`**
- 来源类型/名称、`title`、`summary`、`link`、`published_at`
- 热度 `heat_score`、综合分 **`score_total`**、`score_breakdown_json`
- 入库时间

### `issue_events`（事件聚合，同一事实多源合并）

- 归属 `issue_id`、稳定键 **`event_key`**（聚类去重用）
- 合并后的 **`canonical_title` / `canonical_url` / `summary_merged`**
- **`category`**（大模型/工具/行业 等分类标签）、**`fact_status`**、**`confidence`**
- 合并排序用 **`score_total` / `heat_score`**、`published_at`
- **`sources_json`**：多来源证据列表（含 `raw_item_id` 等）
- **`enrichment_json`**：预留扩展（后续 Verifier 等可写入）

### `send_logs`（发送记录）

- 哪一位订阅者、哪一期、何种 kind（用于去重，防同一期重复发）

### `admin_users`（后台管理员）

- 用户名、密码哈希、是否启用、登录时间等

### `rss_sources`（后台 RSS 信源）

- 后台可增删、启停的 RSS 源
- `channel` 和 `tier` 决定抓取频道与来源优先级
- 表为空时，爬虫回退使用 `.env` 中的 RSS 配置

## 三、数据流简述（便于对照）

### 生产路径（`WEEKLY_SOURCE=global_events`，推荐）

1. **`daily_rankings`** → **`raw_items`**（`issue_id` 为空）→ **`global_events`** + `recalculate_global_event`。  
2. 可选 **`enrich_rankings`** → Ranking Insight 写入 `global_events` 解读字段。  
3. 日榜 API 读 **`global_events`**（Pulse / 7d·30d 综合分，见 [`docs/SCORE_AND_RANKING.md`](SCORE_AND_RANKING.md)）。  
4. **`generate_weekly`** → `weekly_event_scores` / `weekly_score` Top3 + payload。  
5. **`send_weekly`** → **`send_logs`**。

### Legacy 路径（已停用，见 `docs/archive/LEGACY_WEEKLY_MULTI_AGENT.md`）

1. **抓取** → 写入 **`raw_items`**（每期 `issue_id`）。  
2. **`rebuild_issue_events`** → **`issue_events`**。  
3. **周报生成** → **`IssueEvent`** 选题池 → **`weekly_issues.payload_json`**。  
4. **发信** → **`send_logs`**。

---

若你只新建库、从未跑过旧迁移，直接执行 **`sql/schema.sql`** 即可得到完整结构；若线上库已存在，请按 **第一节** 增量执行 `2026-05-02_issue_events.sql`。
